# Fortress Incident — Serialized Work Collapsed Under Token Exhaustion

Date: 2026-08-13
Authority: Drew Clarke
Status: OPEN REGRESSION / DOCTRINE INPUT

## Failure
Fortress expanded grand plans into large scripts and long conversational planning, exhausted hosted inference/context, lost sane serialization, and left the operator with promises instead of usable capability. The operator had to repeatedly invoke Fortress doctrine and transport commands manually.

## Binding correction
`Fortress online` is an invocation shortcut, not a prerequisite for competent operation. Every worker must recover durable project/runtime truth when material context is missing.

Work must default to the smallest usable, evidence-backed increment. Do not turn a broad vision into a mega-script merely because all requested ideas are related. Preserve the full commission in durable state, but execute one bounded dependency-unlocking slice at a time.

A response boundary, context limit, token drought, worker crash, shell death, or operator absence is not mission completion. Before such a boundary can strand work, persist: current objective, exact constraints, current capability state, receipts, blocker, and deterministic next action. Continuation must be recoverable without reconstructing the campaign from chat.

## Hunger pass
Assume the model becomes forgetful, lazy, context-starved, wrong, or unavailable. The operator must never become synchronization middleware. Therefore campaign state and next action must be mechanically recoverable from persistent evidence, and token drought must degrade toward deterministic/local execution rather than toward narration or abandonment.

## Hyperbolic pass
Assume every omission compounds: multiple campaigns, overlapping names, failed connectors, stale branches, out-of-order receipts, frozen shells, exhausted inference, and confident guesses. Therefore:

- retrieve before guessing when durable truth exists;
- serialize execution by dependency and user-visible value;
- checkpoint after every accepted increment;
- treat promises, plans, source, tests, deployment, callability, delivery, and acceptance as distinct states;
- never allow a checkpoint or bounded wave to masquerade as terminal completion;
- never require a magic phrase to activate these rules.

## Canary contract
This incident is not closed by prose. Regression coverage must prove:

1. missing conversational context triggers durable retrieval rather than invention;
2. a large commission produces a durable backlog plus one smallest executable slice, not one giant generated script;
3. context/token exhaustion preserves a restartable checkpoint with exact next action;
4. `CONTINUE_REQUIRED` cannot become success/stop merely because a worker response ended;
5. a worker crash/restart reconstructs the same campaign, constraints, capability state, and next action;
6. stale or out-of-order receipts cannot advance capability state;
7. an unavailable remote inference lane degrades to the authorized deterministic/local continuation policy without silently spending or substituting lanes;
8. the operator is never required to paste internal orchestration prose as shell commands;
9. Chromium Throne remains tomorrow's first delivery gate until it is runtime-canary proven, not merely source-green;
10. two real Chromium Throne interface-evolution generations with persistent receipts are required before calling the Throne usable.

## Immediate delivery gate
Chromium Throne is first. Current source already has an installer and runtime-canary contract. Fix false/red canaries before adding architecture. Then prove installation, launch, authenticated persistent Pro worker identity, one real task, continuation across a checkpoint, and two real interface-evolution generations with persistent receipts.

No downstream feature work may be reported as compensating for an unproven Chromium Throne gate.
