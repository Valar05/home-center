## Proposed implementation lane
1. Reuse the explicitly bound existing authenticated Chromium Throne tab and isolated browser endpoint; do not create tabs, log into accounts, or disturb ordinary Chrome, original CDP 9234, canonical audio services, or the Home Center main checkout.
2. Put a **passive CDP Network observer** alongside the isolated browser session. First probe `Network.streamResourceContent` and `Network.dataReceived.data` on a harmless ChatGPT canary; these DevTools Protocol fields are experimental and actual support must be verified on the installed Chromium. Existing `Network.responseReceived` identifies the response; `Network.eventSourceMessageReceived` may be useful if the app uses EventSource. Do not infer that `Network.getResponseBody` provides live streaming or that Chrome `webRequest` exposes response bodies.
3. Observe only the one authorized tab/target, the expected ChatGPT origin, and its answer-bearing Fetch/EventStream request(s). No TLS man-in-the-middle, certificate replacement, outbound proxy, cookie/header/token collection, indiscriminate packet capture, raw HAR storage, or interception of other tabs. CDP is an implementation technique for network bytes, *not* DOM or page text extraction.
4. Decode transport bytes incrementally with stateful UTF-8, SSE framing across arbitrary chunk boundaries and a versioned schema adapter. Identify assistant-visible final-channel text by protocol roles and turn IDs; exclude hidden reasoning, tool payloads, prompts, unrelated events and authentication material. If response schema is unknown, stop voice dispatch, save only redacted structural/size/timestamp diagnostics, and request an authorized minimal canary. Never guess the answer from timing or DOM.
5. Order speech by existing **agent-authored complete paragraphs**, not byte arrival or model tool calls. The observer must preserve actual paragraph boundaries and never resegment by punctuation, sentence regex, fixed characters or text size. Current Pocket ticket ceiling is **450 characters**. If the agent already authored a paragraph longer than the ceiling, mark that speech unit BLOCKED and provide an exact missing span; do not silently split, truncate, synthesize a substitute or lose the remainder. For stable already-authored units, queue the first two promptly when available, rather than awaiting the first WAV or playback; keep exact draft revisions/deltas and avoid duplicates. If stability is uncertain, defer rather than playing an overwritten draft. Validate exact full substantive visible/spoken coverage, including roleplay narration. `ritsu-voice-return.mjs`'s older character-based splitter is forbidden.
6. The observer sends owner-authenticated, bounded turn/segment records through Home Center. Define a network-provenance ingress/result contract or extend an existing *typed* one without impersonating `ritsu.chat.publish`'s model-origin callback. New stream records need sessionId, turnId, channel, browser request identity, revision, ordinal, text hash, source, explicit final state; at-most-once delivery receipts and recovery after unknown ACKs. The initiating CONTROL session reads exact final text and provenance through MCP.
7. Voice dispatch goes through live typed Home Center `ritsu.voice.speak` with verified Pocket repertoire profile (`normal` by default) and the existing THECAULDRON Pocket TTS `127.0.0.1:10205`, same canonical localhost/Tailscale 19643 relay and Termux receiver. The old cloud `voice='warm-v1'` field is schema compatibility, NOT authorization to use the retired Qwen engine. No Pocket model start/restart, new GPU process, other TTS, phone-shell transport or alternate audio relay. Agent-authored units have independent stable request IDs with exact text/profile/hash; recover ambiguous outcomes by status before retrying. The receiver remains v3 with unaccepted gaps; v4 is on HOLD.
8. Visibility and recovery: persist minimal nonsecret delivery receipts `OBSERVED -> DECODED -> TEXT_FINAL -> SPEECH_ACCEPTED -> ENQUEUED -> PHONE_ACKED -> HEARD (user verdict)`. Stop/retry at the exact failed gate without blindly re-sending ambiguous text or speech. A response being visible in the browser is not proof its text was observed on the stream; enqueue is not proof user heard it.
