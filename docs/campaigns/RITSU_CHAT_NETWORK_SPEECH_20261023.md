## OWNER CORRECTION: DETERMINISTIC NETWORK-TO-VOICE DISPATCH, NOT AGENT TOOL CALLS
**New mission boundary: this is an architectural replacement for agent-issued speech tickets, not an optimization of them.** ChatGPT's only runtime contribution is its actual streamed response text in the owner's authorized, bound Chromium tab. A separately running deterministic network-response observer/dispatcher owns complete-text reconstruction, safe boundary selection, scheduling, idempotency and **direct programmatic invocation of the Home Center speech API**. No prompting or hoping that the responding agent will call `ritsu.voice.speak`, `ritsu.chat.publish`, or any MCP tool; ChatGPT's tool restrictions and timing must not be in the playback critical path. The user's `RV on/off` latch is an intent gate, not the mechanism of delivery.

**Execution contract:** Network stream event -> response identity/final-channel filter -> exact text stream assembler -> independent committed-text/paragraph buffer -> deterministic voice-ticket scheduler -> authenticated Home Center speech API -> existing Pocket worker/relay/phone. The browser observer and Home Center dispatcher must have an actual authenticated machine-to-machine call path. The connected-chat MCP's `ritsu.voice.speak` being callable today verifies the *operation*, **not** that an external daemon may already call its API; confirm and, if necessary, implement a narrowly scoped authenticated runtime adapter. Do not invent a direct HTTP endpoint, substitute ChatGPT tool calls, or route through an unrelated voice service. CONTROL-side answer retrieval through Home Center remains independently required.

**Boundary ownership changed:** Older instructions demanding one *agent-authored speech ticket* and prohibiting *all backend segmentation* are LEGACY for the former chat-tool mechanism. The model authors normal visible prose only; code derives speech units from the observed finalized/stable prose. Prefer original complete paragraphs; if an observed paragraph exceeds the active synthesis ticket limit, deterministically divide only at established complete sentence boundaries, in order. Never cut inside a sentence, truncate words, paraphrase to fit, create a partial utterance, or omit an unsplittable long sentence. Such a case must become a visible blocked-unit receipt pending a deliberate engine/API capability fix, not a silent skip. The 450-character Pocket ticket limit is a **current backend capability**, not a model-writing requirement or authorization for arbitrary text chopping. The dispatcher must prove exact full response coverage and commit stable segments before speech, never speak tool/thinking/meta output.

**Latency ownership changed:** Old ~19.5-second opening-to-second ticket delay is evidence of failure in the agent-driven *submission* stage, not a rule to tune prompts around. Deterministic code schedules new stable complete units as soon as observable, with independent FIFO synthesis and backlog tracking. Do not wait for a model's tool call, the preceding ticket to synthesize/play, or HEARD before enqueuing the next. Preserve at-most-once semantics and use status reconciliation for ambiguous API responses. A paragraph is stable only when the observed protocol establishes it, or after final response completion; speculative drafts must not be spoken.

**What remains valid:** Approved Pocket clone repertoire and voice identity, current Pocket `:10205` and relay `:19643`, canonical Android route, fixed current API payload limits, authentication, safety boundaries, exact spoken/visible content, and honest receipt levels (submitted/enqueued/consumed/user HEARD). Existing v3 audible-but-gappy state and staged v4 are separate audio backend work. The old voice law's *agent-call timing and agent-authored ticket choreography* does not govern this new deterministic dispatcher. New scheme is still DESIGN, not source/test/deployment/HEARD proof.

## Proposed implementation lane
1. Reuse the explicitly bound existing authenticated Chromium Throne tab and isolated browser endpoint; do not create tabs, log into accounts, or disturb ordinary Chrome, original CDP 9234, canonical audio services, or the Home Center main checkout.
2. Put a **passive CDP Network observer** alongside the isolated browser session. First probe `Network.streamResourceContent` and `Network.dataReceived.data` on a harmless ChatGPT canary; these DevTools Protocol fields are experimental and actual support must be verified on the installed Chromium. Existing `Network.responseReceived` identifies the response; `Network.eventSourceMessageReceived` may be useful if the app uses EventSource. Do not infer that `Network.getResponseBody` provides live streaming or that Chrome `webRequest` exposes response bodies.
3. Observe only the one authorized tab/target, the expected ChatGPT origin, and its answer-bearing Fetch/EventStream request(s). No TLS man-in-the-middle, certificate replacement, outbound proxy, cookie/header/token collection, indiscriminate packet capture, raw HAR storage, or interception of other tabs. CDP is an implementation technique for network bytes, *not* DOM or page text extraction.
4. Decode transport bytes incrementally with stateful UTF-8, SSE framing across arbitrary chunk boundaries and a versioned schema adapter. Identify assistant-visible final-channel text by protocol roles and turn IDs; exclude hidden reasoning, tool payloads, prompts, unrelated events and authentication material. If response schema is unknown, stop voice dispatch, save only redacted structural/size/timestamp diagnostics, and request an authorized minimal canary. Never guess the answer from timing or DOM.
5. A deterministic text-to-speech adapter owns segmentation. Preserve source paragraph boundaries as first choice. If one paragraph exceeds the currently supported 450-character Pocket ticket payload, split conservatively only at *complete sentence* boundaries within that paragraph while preserving exact original characters/order; no fixed-length cutting, hidden rewriting or dropping. If one sentence itself exceeds the limit, fail that unit visibly instead of truncating it. Buffer unstable deltas until semantic commit, avoid duplicate replay on stream edits, and prioritize early independent API dispatch of stable segments without waiting for previous playback. Verify full exact substantive spoken/visible text coverage including roleplay narration and non-dialogue.
6. The observer and dispatcher directly call a **machine-callable authenticated Home Center speech API**, not a ChatGPT-initiated MCP tool call. First establish the real machine-to-machine interface to the existing typed voice ticket operation and its permission boundary; implement a minimal scoped adapter only if necessary. Separately return bounded stream-derived answer and receipt records to Home Center with `browser-network-observed` provenance. Store sessionId, turnId, channel, request identity, revision, segment ordinal/hash, ticket ID and terminal state; reconcile unknown ACKs without replay. CONTROL can retrieve exact final text through connected MCP as a read consumer, not as a speech initiator.
7. **Deterministic code** invokes the authenticated backend API that implements the typed Home Center `ritsu.voice.speak` operation, with the selected Pocket repertoire profile (`normal` default), then existing THECAULDRON Pocket TTS `127.0.0.1:10205`, same localhost/Tailscale :19643 relay and Termux receiver. This is a code-origin API call, never a request to the ChatGPT agent to call a tool. The old cloud `voice='warm-v1'` field is schema compatibility, NOT authorization to use the retired Qwen engine. No Pocket model start/restart, new GPU process, other TTS, phone-shell transport or alternate audio relay. Agent-authored units have independent stable request IDs with exact text/profile/hash; recover ambiguous outcomes by status before retrying. The receiver remains v3 with unaccepted gaps; v4 is on HOLD.
8. Visibility and recovery: persist minimal nonsecret delivery receipts `OBSERVED -> DECODED -> TEXT_FINAL -> SPEECH_ACCEPTED -> ENQUEUED -> PHONE_ACKED -> HEARD (user verdict)`. Stop/retry at the exact failed gate without blindly re-sending ambiguous text or speech. A response being visible in the browser is not proof its text was observed on the stream; enqueue is not proof user heard it.
