# PUNIT PUNCHLINE TERMINAL — UNIVERSAL OS PRESENTATION CONTRACT

Status: binding commission
Custody: Adam under TOUCHED IT -> OWN IT
Presentation: Venice narrates verified state; Punit owns the terminal punchline

## Commission
Every user-facing part of the operating system ends in a Punit punchline. This is a presentation-layer invariant, not permission to corrupt operational state or evidence.

Punit is whole. The implementation must preserve the established Punit character and communication grammar, including his Tourette's/tic expression as part of the character rather than sanitizing him into a generic joke generator. The system must not treat Tourette syndrome itself as the joke, fabricate medical claims, or reduce Punit to involuntary profanity. Humor comes from Punit's character, timing, interpretation, word collisions, callbacks, literalism, narrative context, and established expressive behavior; tics may participate naturally where consistent with canon.

## Terminal pipeline
VERIFIED EVENT/STATE -> VENICE CARE/NARRATION -> ACCESSIBLE PLAIN STATE -> MORSE SIGNAL WHEN APPLICABLE -> PUNIT TERMINAL PUNCHLINE.

The punchline is downstream of truth. It may reinterpret, roast, compress, callback, pun, misdirect, or Fleshpunk the event. It may never alter the receipt, hide a blocker, invent delivery, or replace a required action.

## Universal applicability
Apply the terminal to every user-facing OS presentation class where a punchline is contextually possible: command results, worker transitions, ticket tending, success/failure receipts, debugging, Wizard DNS resolutions, Joy delivery, reminders, alerts, mining discoveries, Inner World narration, Outer World narration, deployment/acceptance transitions, Morse explanations, and ordinary status surfaces.

Critical safety/authority messages retain a clear unambiguous plain statement before the punchline. Accessibility requires the semantic state to remain independently understandable without parsing the joke.

## Punit state
Punit is not a stateless template. Maintain a compact durable presentation state sufficient for callbacks and variation:
- recent punchline fingerprints to avoid accidental repetition;
- accepted recurring bits/callbacks;
- current narrative/Inner World context;
- entities/objects available for wordplay;
- current Morse/event semantic;
- intensity/appropriateness gate;
- established Punit canon and speech/tic grammar;
- user KEEP/REJECT feedback where available.

Intentional recurrence is allowed when the callback itself is the joke.

## Generation / deterministic decay
Prefer a layered system:
1. deterministic punchline templates/callback rules for common known events;
2. indexed Punit vocabulary/grammar transformations;
3. local low-inference generation for novel contexts;
4. stronger inference only when novelty/value justifies it;
5. harvest successful novel punchlines into cheaper reusable rules.

Repeated OS events should get funnier and cheaper over time, not require permanent high inference.

## Quality gate
No obligation is discharged by appending a random pun. The terminal must be recognizably Punit, tied to the actual event, concise enough not to bury the result, and worth the latency/cognitive cost. Noodle Lady/taste and Joy feedback govern retention. Bad punchlines become negative fixtures.

## API shape
User-facing API/presentation envelopes should support separate fields/objects for operational truth and presentation, conceptually:
- `state` / `receipt` — machine truth;
- `narration` — Venice/care explanation;
- `morse` — semantic telemetry when applicable;
- `punit` — terminal punchline payload;
- `accessibility` — concise equivalent/labels as needed.

This document defines the contract; it does not claim those fields are already implemented in Home Center.
