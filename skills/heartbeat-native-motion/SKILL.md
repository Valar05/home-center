# Heartbeat Native Motion

## Purpose
Turn semantic heartbeat transition truth into one bounded native visual consequence without allowing polling, evidence refresh, visibility restore, or taste to manufacture Christmas blinking.

This skill is source doctrine for the existing Operator Overlay. It does not own a renderer, controller, phone lane, P0 recovery path, or deployment authority.

## Canonical inputs
Consume the already-accepted `HeartbeatSceneGraph.Frame` / `HeartbeatOverlayViewModel.Model` only. Do not infer motion from timestamps, poll frequency, labels, colors, raw payload arrival, or reviewer enthusiasm.

A node may receive one native cue only when all of these are true:

- `node.transitionMotion == true`;
- `frame.transitionMotionAllowed == true`;
- the heartbeat/details surface is actually presented;
- platform animators are enabled.

If any gate is false, motion is blocked. Revealing a surface later must not replay a transition first observed while hidden/collapsed. Exact retry and evidence/provenance-only refresh earn no motion.

## Pure-removal rule
A material removal changes frame structure but the removed node no longer exists. Do not invent a replacement light merely to animate it.

When `frame.transitionMotionAllowed == true` and no surviving/added node owns `transitionMotion`, the existing heartbeat summary is the only honest fallback surface for one bounded cue. Additions and state/consequence changes already have a node owner and must not double-pulse the summary.

## Accessibility and reduced motion
Motion is supplementary only. State remains available through non-color tokens, text, touch detail, and TalkBack semantics.

- platform animation disablement is authoritative;
- no autoplay loop;
- no repeating blink;
- no motion required to understand state;
- no speech is generated by this skill;
- motion does not change selection, keyboard focus, TalkBack focus, operator authority, or execution state.

The current pure policy uses a short one-shot cue contract (`140ms`, start scale `0.96`, start alpha `0.72`) so a future existing-owner application can settle back to the native control's ordinary geometry before the 200ms polling heartbeat would normally consider another source update. Those constants are source policy, not proof that Android displayed them.

## Existing organs
- semantic truth: `HeartbeatSceneGraph`
- UI-ready projection: `HeartbeatOverlayViewModel`
- pure decision policy: `HeartbeatNativeMotionPolicy`
- native owner: existing `OperatorOverlayService`
- source teaching organism: `docs/try-forever/heartbeat-motion-clamp-source-specimen.html`

Do not create a neighboring animator service/controller. The existing owner must consume the policy if/when owner wiring is authorized and reviewable.

## Evidence membrane
Keep these states separate:

1. requested;
2. semantic scene motion source;
3. pure native motion policy source;
4. UI-ready motion projection source;
5. regression source;
6. existing-owner consumption;
7. tested;
8. runtime visually observed;
9. deployed;
10. callable/executed;
11. delivered;
12. accepted.

A DOM/SVG specimen proves source art only. A Java policy proves source policy only. Regression files prove regression source only until a test runner executes them. None of those proves phone delivery.

## P0 firewall
This skill never consumes Phone Hands, the primary-phone execution surface, recovery queues, Nightcore, Pocket TTS, Chromium, Context Organs, or the physical acceptance chain. P0 evidence is read-only here.

## Current source boundary
`HeartbeatNativeMotionPolicy`, `HeartbeatOverlayViewModel` motion projection, regression source, and the warm-wall teaching organism exist on the TRY FOREVER branch. The existing `OperatorOverlayService` does **not** yet consume the new policy. Therefore native motion runtime behavior, reduced-motion runtime behavior, deployment, delivery, and acceptance remain unproven.
